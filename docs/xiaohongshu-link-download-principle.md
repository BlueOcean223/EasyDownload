# 小红书链接解析下载原理

本文档说明 EasyDownload 中小红书“根据分享链接解析并下载”的完整链路。和抖音相比，小红书实现更偏页面抓取：先从分享文本里拿到 `note_id` 和可能存在的 `xsec_token`，再直接请求笔记页面，最后从页面脚本里提取结构化数据。

## 1. 适用范围

当前这套链路处理的是“用户已经拿到小红书分享文本、短链或完整笔记链接”的场景，不处理搜索、推荐流抓取、登录态托管或评论翻页采集。

支持的输入包括：

- 小红书分享文本
- `xhslink.com` 短链
- 完整笔记链接
- 直接输入 24 位十六进制 `note_id`

核心代码：

- `internal/download/xiaohongshu/parser.go`
- `internal/download/xiaohongshu/client.go`
- `internal/download/xiaohongshu/downloader.go`
- `app.go`
- `frontend/src/views/Xiaohongshu.vue`

## 2. 总体流程

一次完整的小红书下载链路可以拆成下面几步：

1. 前端接收用户输入的小红书分享文本或链接
2. `Parser` 提取 URL，必要时展开短链
3. 从 URL 中提取 `note_id`
4. 同时保留 `xsec_token` 和完整 URL
5. `Client` 请求 `/explore/{noteID}` 页面
6. 从 HTML 中提取 `window.__INITIAL_STATE__`
7. 解析出笔记详情，构建 `XHSItem`
8. 前端展示封面、作者、标题、图片或视频清晰度
9. 用户点击下载后，前端把 `XHSItem` 直接传回后端
10. `Downloader` 按笔记类型输出 `.mp4` 或 `.zip`

这里和抖音最大的结构差异是：小红书在下载时不重新解析原始分享文本，而是直接使用前端已经拿到的 `XHSItem`。

## 3. 解析阶段

### 3.1 允许直接输入 `note_id`

解析器首先支持一种抖音没有的输入方式：

- 如果用户输入本身就是 24 位十六进制字符串，直接把它当 `note_id`

这对调试和内部调用很方便，因为某些场景下你已经知道笔记 ID，不需要再绕一遍链接解析。

### 3.2 从分享文本提取 URL

如果输入不是纯 `note_id`，解析器会：

1. 去掉首尾空白
2. 如果整段文本本身像 URL，就优先按 URL 解析
3. 否则从整段分享文本中用正则提取 `http/https` 链接
4. 只接受小红书域名和已知短链域名

### 3.3 短链展开

小红书短链通常是：

- `xhslink.com`
- `www.xhslink.com`

这一步比抖音复杂，因为它不一定总是标准重定向。

解析器会先尝试标准方式：

1. 发起 `GET`
2. 关闭自动跳转
3. 如果响应是 `3xx`，读取 `Location`

但如果短链没有返回标准 `3xx`，还会继续兜底：

1. 读取返回的 HTML
2. 把 HTML 里的实体字符反转义
3. 在 HTML 文本里继续提取小红书真实链接

也就是说，小红书短链解析包含两种模式：

- 标准 3xx `Location` 重定向
- 非 3xx HTML 页面内嵌真实链接

### 3.4 为什么要保留 `xsec_token`

小红书解析结果不只是 `note_id`，还会保留：

- 完整 URL
- `xsec_token`

原因是很多分享链接里带的 `xsec_token` 对后续访问笔记页有帮助。当前客户端获取详情时会优先把它拼回到 `/explore/{noteID}` 上，提升页面抓取成功率。

所以小红书解析阶段的目标不是“只拿一个 ID”，而是“拿到足够还原页面访问上下文的信息”。

## 4. 信息抓取阶段

### 4.1 直接抓笔记页面

和抖音不同，小红书不是先打接口，而是直接请求：

- `/explore/{noteID}`

如果解析阶段拿到了 `xsec_token`，会带上：

- `?xsec_token=...`

这一层默认假设：页面里已经带有渲染笔记详情所需的数据。

### 4.2 模拟浏览器请求

客户端会为页面请求补齐一组更接近浏览器导航的请求头，例如：

- `User-Agent`
- `Referer`
- `Accept`
- `Accept-Language`
- `Accept-Encoding`
- `Sec-Fetch-*`
- `Upgrade-Insecure-Requests`

这是因为小红书页面态抓取对“像不像浏览器”比普通 JSON 接口更敏感。

### 4.3 处理压缩响应

小红书页面响应可能是压缩的，客户端专门处理了：

- `gzip`
- `br`
- `deflate`

其中 `deflate` 还兼容了两种服务器实现：

- zlib 包装
- 原始 deflate

同时还设置了最大 HTML 解压大小上限，避免异常响应把内存打满。

### 4.4 从 `__INITIAL_STATE__` 提取笔记数据

拿到 HTML 后，客户端会：

1. 检查是否是“笔记不可浏览”之类的错误页
2. 从页面里提取 `window.__INITIAL_STATE__`
3. 把 JavaScript 对象修正为合法 JSON
4. 反序列化为通用 map 结构
5. 从 `note.noteDetailMap[noteID].note` 中找到目标笔记

这一步本质上是在利用小红书页面 SSR 或首屏注水数据，而不是调用公开 JSON API。

### 4.5 构建 `XHSItem`

客户端拿到笔记对象后，会把它统一映射成 `XHSItem`，核心字段包括：

- 笔记 ID
- 标题
- 描述
- 作者名
- 作者 ID
- 作者头像
- 时间戳
- 发布地 `ipLocation`
- 标签列表 `tagList`
- 互动数据 `interactInfo`
- 类型
- 视频流列表
- 图片列表
- 封面

## 5. 内容类型判断

### 5.1 视频笔记

如果笔记类型是视频，或者解析出了视频流，就会构造成：

- `Type = video`

同时带出：

- 清晰度列表
- 每个流的主 URL 和备用 CDN URL
- 分辨率
- 文件大小
- `fps`、`videoCodec`、`videoBitrate`、`audioCodec`、`audioBitrate`
- `streamDesc`、`streamType`、`weight`、`duration`、`hdrType`、`rotate`

小红书目前常见的视频 `stream` 字段既可能是旧数组，也可能是按 codec 分组的新对象，例如 `h264`、`h265`、`av1`、`h266`。实现会兼容两种结构，并用 `streamType` 生成更稳定的清晰度 key（例如 `hd_115`），避免多个实际不同的流都被折叠成同一个 `HD`。

流排序优先级是：有可下载 URL > codec（默认只明确偏好 H.265/HEVC，其次 H.264；AV1/H.266 暂不自动排到最前，避免兼容性问题）> 官方 `weight` > 已知 `streamType` 档位 > `defaultStream` > 分辨率 > 码率/大小。这样默认会优先选择同画质下体积更小的 H.265 流，或者同体积下更高分辨率的 H.265 流。

### 5.2 图文笔记

如果解析出了图片列表而没有视频流，就会构造成：

- `Type = image`

并附上图片数组。图片 URL 优先级是 `urlDefault > urlPre > url > infoList`，同时会保留其余 URL 作为备用下载地址。第一张图片会作为封面。

如果图片带有 Live Photo 视频流，也会解析出 `LivePhotoURL`；下载图集时会在 ZIP 中同时保存静态图和对应的 `_live.mp4` 视频副本。

### 5.3 未知类型

如果既没有视频流，也没有图片列表，客户端会把内容标记成：

- `Type = unknown`

这是一种防御式处理，避免页面字段轻微变化时直接把整个解析链路打断。

## 6. 下载阶段

下载器通过 `XHSItem` 的类型决定走视频还是图文路径。

### 6.1 视频下载

视频下载的处理顺序是：

1. 按前端传入的 `quality` 选流
2. 如果没匹配上，就回退到第一个可用流
3. 先尝试 `masterUrl`
4. 如果主 URL 失败，依次尝试 `backupUrls` 里的备用 CDN
5. 调用通用可续传下载逻辑
6. 传入 `User-Agent` 和 `Referer`
7. 支持断点续传和 Range
8. 持续回调字节级进度

下载器额外带了两层保护：

- 视频大小上限，默认 2GiB
- 无进度超时，默认 2 分钟

这样可以避免异常响应、假死连接或超大文件把下载任务长期卡住。

### 6.2 图文下载

图文下载会：

1. 校验用户选择的图片索引
2. 创建图集临时目录和状态文件
3. 检查历史已完成项是否还存在（Live Photo 会同时检查静态图和视频副本）
4. 顺序下载每一张图，主图片 URL 失败时尝试备用 URL
5. 如果图片包含 Live Photo，继续下载对应视频副本
6. 每完成一批就保存状态
7. 全部完成后打成 ZIP
8. 清理临时目录

当前小红书图文下载是顺序执行，不走并发抓取。这和抖音图集的并发下载策略不同。

### 6.3 局部下载

前端也可以只选择部分图片进行下载。下载器会把用户选择标准化成索引集合，只对这些图片生成 ZIP。

因此图文笔记既支持：

- 下载全部图片
- 下载部分图片

## 7. App 和前端的调用方式

### 7.1 前端页面

小红书页面的交互是：

1. 用户在 `frontend/src/views/Xiaohongshu.vue` 输入分享文本或链接
2. 点击“解析”后调用 `GetXHSNoteInfo`
3. 前端拿到完整 `XHSItem`
4. 如果是视频，则展示清晰度
5. 如果是图文，则展示图片网格和局部选择器
6. 点击下载时，把 `XHSItem` 原样传回后端

### 7.2 App 层接口

后端暴露的主要方法有：

- `GetXHSNoteInfo`
- `DownloadXHSNote`

`GetXHSNoteInfo` 的特点是：

1. 先通过 `ParseWithURL` 拿到 `note_id + xsec_token`
2. 再调用 `GetNoteInfoWithToken`

`DownloadXHSNote` 的特点是：

- 它不重新解析原始输入
- 它直接接收前端传回来的 `XHSItem`
- 视频和图文都通过统一的 `BuildDownloadFunc` 进入下载管理器

### 7.3 下载管理器集成

和抖音一样，小红书下载最终也会进入通用 `DownloadManager`。这样能统一：

- 任务队列
- 进度事件
- 完成事件
- 失败事件
- 文件命名和输出路径

但是小红书这一侧在进入下载器之前，信息对象已经完整结构化了，因此下载时少了一次重新抓详情的开销。

## 8. 常见失败点

小红书链路常见失败点主要有下面几类。

### 8.1 解析失败

常见原因：

- 输入里没有小红书 URL
- URL 不是小红书域名
- 短链既没有返回 3xx，也没在 HTML 里找到真实链接
- 没提取到 24 位 `note_id`

### 8.2 页面抓取失败

常见原因：

- `xsec_token` 缺失或失效
- 页面返回 401/403，说明需要登录或内容受限
- 页面返回 429，被限流
- HTML 里没有 `window.__INITIAL_STATE__`
- 页面脚本结构变化，导致 `noteDetailMap` 定位失败

### 8.3 下载失败

常见原因：

- 视频流地址为空
- 主 URL 和备用 CDN URL 都下载失败
- 视频体积超过限制
- 下载过程中长时间无进度被主动中断
- 某张图片主地址和备用地址都返回异常状态码
- Live Photo 视频副本下载失败或超过大小限制
- ZIP 打包或临时目录写入失败

## 9. 这套实现的特点

小红书当前实现的工程特征可以概括为：

- 输入兼容短链、长链和纯 `note_id`
- 解析阶段会尽量保留页面访问所需上下文，尤其是 `xsec_token`
- 抓取阶段依赖 HTML 页面，不依赖公开 JSON 接口
- 对压缩格式、页面脚本和异常页做了较多兼容
- 图文下载重视稳定性和恢复，而不是极限吞吐
- 下载时直接使用前端已经解析好的结构化对象

如果后续要扩展小红书搜索、登录态或更复杂的页面交互，建议在现有“分享链接解析下载”链路之外，单独增加新的浏览器态抓取模块，而不是把这些职责继续堆到当前 `Parser/Client` 上。
